# Design: zullumap — agent-first, remixable 3D map templates

Generated by /office-hours on 2026-11-19 · Revised 2026-11-20 (3D-first interactive, deck.gl foundation)
Branch: main
Repo: jjestrada2/zullumap
Status: APPROVED
Mode: Builder (open-source community project first; started in startup mode, switched after the landscape check)

## Problem Statement

GIS analysts can do the analysis but lose hours on the last mile: page size, viewports, symbology, legends and animation. The builder, a GIS technician (ArcGIS Pro at work; QGIS + Google Earth Engine for #30DayMapChallenge and hackathons), described it this way: "I'm good doing the geospatial analysis, but I don't like to spend hours choosing symbology or creating animations... I would love just to choose a style template and just plug in my data and present it." At work, "a quick map... is made with a pre-existing template, otherwise it would be a large project."

Today's workaround is asking Claude to build a one-off standalone website for each map. It works and costs nothing, but every result is one-off: no reusable style, nothing to share, and no consistency between maps.

The original pitch ("Canva for maps" for non-cartographers) was dropped after the landscape check: Datawrapper, Flourish, Felt and Google My Maps already serve non-experts clicking a UI. What is not served is reusable, shareable cartographic style that an AI agent can apply.

The project's visual inspiration is a community-made interactive 3D map built with three.js. So zullumap is **3D-first and interactive**: the map people make is a living 3D web page, not a static image.

## What Makes This Cool

- **A 3D map style becomes a file an agent can apply to any data.** A template is the whole experience: 3D layers, colors, camera, lighting, layout (title, legend, credits) and a fly-through.
- **Remix this style (the chosen "whoa" moment).** Every map carries its template. Someone watches a 10-second fly-through on LinkedIn, scans the QR code on its end card (or clicks the link in the caption), lands on the template page with the original map's choices loaded, and gets the same 3D look on their own data in minutes. Every published interactive map page also has its own "Remix this style" button.
- **Plugged into the deck.gl ecosystem.** Templates compile to deck.gl's JSON spec, a format AI agents and CARTO's agent tools already speak, so zullumap adds taste and reuse on top of a standard instead of a new engine.

## Constraints

- Solo builder with a full-time GIS job; v1 has to be buildable in days with Claude Code, not months.
- Open source and community-first; money comes later (team template kits, hosted rendering), not in v1.
- Build on existing engines: **deck.gl + MapLibre**, used as dependencies, never forked. No custom renderer, no new style language.
- v1 input: vector data only (GeoJSON, CSV with lat/lon). Rasters (GEE exports) are deliberately deferred.
- v1 output: interactive 3D web pages plus fly-through trailers. No static PNG/PDF maps.

## Premises (agreed)

1. First users are people with finished data: the builder and the #30DayMapChallenge / hackathon crowd (mostly GIS people). Non-experts arrive later through the remix gallery.
2. **(Revised for 3D)** A template is the whole interactive experience: 3D layers + colors + camera and lighting + page overlay (title, legend, credits, remix button) + a fly-through camera path, built on the deck.gl JSON spec, a MapLibre basemap style and HTML/CSS.
3. **(Revised after the second opinion)** Templates declare explicit adaptation rules (allowed class methods, height scale range, zoom and pitch ranges, title length, supported geometry types); agents choose only inside those rules. The moat is taste + the slot standard + the remix network, not taste alone.
4. **(Revised for 3D)** Output is a self-contained interactive 3D web page the user owns and can host anywhere, plus an auto-recorded fly-through trailer (MP4) that exists only to drive clicks to it. zullumap does not host live maps for users or run analysis; that stays in Felt, CARTO, kepler.gl, GEE, QGIS.
5. Ships as an open-source CLI + agent skill (MCP later) + a gallery website where remix starts. Launch target: #30DayMapChallenge.
6. One-off Claude-built maps prove generation already works; the gap is reuse and consistency, not generation.
7. **(New)** deck.gl is the engine, not the competitor. zullumap builds on deck.gl + MapLibre and never forks them; three.js effects come later through custom layers.

## Landscape (Nov 2026)

- **Engines:** deck.gl (MIT, vis.gl / OpenJS) draws 3D data layers (extrusions, columns, arcs, terrain, millions of points) and interleaves with MapLibre. three.js is a general 3D engine with no geography built in.
- **Closest neighbors built on deck.gl:** kepler.gl (MapLibre + deck.gl) makes interactive 3D maps, exports a self-contained HTML map and a map config JSON (layers, filters, map style, interactions), and has an AI assistant that adds layers and changes colors. CARTO's open-source `@carto/agentic-deckgl` teaches agents to write deck.gl JSON specs, and CARTO's MCP app renders them in Claude. So "an agent makes an interactive deck.gl map" already exists.
- **Other agentic map tools:** Felt's official MCP/Claude connector, Mapbox MCP server, maplibre-mcp, a FOSS4G 2026 paper that auto-generates MapLibre styles.
- **Themed pretty-map generators** (prettymaps/prettymapp, MapToPoster) prove demand for "pick a theme", but only draw OpenStreetMap city streets, not the user's own data.
- **The gap:** every tool above lets the agent or person invent the look from scratch each time, and kepler.gl configs are one map's app state (no slots, adaptation rules, layout or remix). Nobody offers designed, reusable, remixable 3D map templates with a community gallery.
- **Risk:** kepler.gl could add a template gallery. Defense: be the community and taste layer and ship fast; the remix network is the hard-to-copy part.
- **Money references for later:** Remotion (free for individuals and companies of up to 3 people; companies pay ~$25/seat/month or $0.01/render with a $100 minimum), Datawrapper Business ($39/user/month), Felt (paid team plans). HyperFrames (HeyGen, Apache 2.0) makes no direct money.

## Cross-Model Perspective (Claude subagent cold read, before the 3D revision)

- **Coolest version:** every output carries its recipe, so any map is a "view source" map: `zullumap remix <map-or-url> --data mine.geojson`. Templates as git repos with CI that renders each one against standard test datasets and shows a "fit score" in the gallery.
- **What excites the builder most:** "each user can publish their own template and make it AI agent first." Publishing and community, more than replacing QGIS. Judge v1 on whether a second person can publish a template.
- **50% already exists:** the renderer. The real work: the slot contract, data fitting, page layout and remix provenance. (After the revision, deck.gl + MapLibre is the renderer.)
- **Challenged premise #3** (agents never invent the look): fitting real data forces design calls anyway. Accepted and revised (see Premises).
- Where I disagreed: GEE rasters must be an early milestone or zullumap can't make the builder's own maps.

## Approaches Considered

### Approach A: Remix Loop MVP (chosen; revised for 3D)
CLI that turns a template + GeoJSON/CSV into a self-contained interactive 3D map page and a fly-through trailer, 3 hand-made 3D templates, one agent skill file, a static gallery, and the remix recipe from day one. Effort S-M (human ~3 weeks / CC ~3-4 days). Completeness 7/10: happy path with vector data.

### Approach B: Template Standard + Community Platform
Written template spec, CLI + MCP server, CI fit scores, community publishing, GEE rasters and terrain, three.js custom layers, HyperFrames-based trailers, hosted rendering later. Effort L. Deferred; it is the upgrade path from A.

### Rejected
- **Approach C, skill-only templates:** output changes run to run, which breaks remix and consistency.
- **Forking deck.gl:** maintaining a large graphics engine alone, losing upstream fixes, for no product value.
- **three.js as the only engine:** would mean rebuilding projections, tiles, terrain and labels.
- **Static PNG/PDF as products:** replaced by the interactive page; the trailer is the only non-interactive output.

## Recommended Approach

**Approach A, built with B's format decisions from day one** (recipe, slot contract, adaptation rules), so nothing is thrown away on the way to B.

**Stack:** TypeScript CLI on Node (Bun-compatible); deck.gl (via `@deck.gl/json`) for 3D data layers interleaved with MapLibre GL JS for the basemap, globe and labels; Protomaps PMTiles basemap; Playwright (headless Chromium) only for recording trailers and running `check`; ffmpeg for encoding; GitHub Pages for the gallery.

**Template = a folder:**
- `manifest.json`: id, version, author, license, **slots** (e.g. `geometry: polygon`, `value: number` for color, `height: number?` for extrusion, `label: string?`, `title: string ≤ 48 chars`), **adaptation rules** (allowed class methods such as quantile / natural breaks, class count, height-scale range, zoom and pitch ranges, label density), camera presets and the fly-through path.
- `deck.json`: a deck.gl JSON spec (layers, colors, extrusion, lighting) that refers to data only through named slot placeholders such as `{{slot:height}}`; `core` turns them into deck.gl accessors through a small set of named helpers registered with deck.gl's JSON converter (e.g. `zmClassColor`, `zmHeight`; eng review D14), and any raw `@@` expression in this file is rejected (eng review D4). Custom math goes in the optional `effects.js`.
- `basemap.json`: a MapLibre style with the template's basemap look.
- `overlay.html`: the HTML/CSS page overlay (title, legend, credits, remix button), with no JavaScript. It must mark its regions with `data-zm-region="title|legend|credits|remix"` so the viewer can move them into the phone bottom sheet (design D2), and trailers use a trailer layout of the same regions inside the safe zones (design D5). It uses a minimal placeholder syntax: `{{title}}`-style text interpolation and one repeat block for legend rows (one row per resolved class); all values are inserted as text, never HTML (eng review outside voice).
- `preview/`: renders on the standard test datasets.

**v1 outputs:**
1. **The interactive map page:** a folder whose `index.html` contains the data, the resolved deck spec and the recipe inlined as JSON script blocks (eng review D5), so it opens by double-click as well as on any static host (GitHub Pages, Netlify, the gallery); `recipe.json` is also written next to it for `remix` URL fetches. It loads deck.gl, MapLibre and zullumap's fixed viewer runtime from a pinned CDN version (D6); the only template code on the page is the template's optional `effects.js`, inlined as a hash-pinned module script so it also works when the page is opened by double-click (eng review D3, D5).
2. **The fly-through trailer:** an MP4 (default 1080×1350, 4:5 for LinkedIn; 10-15 s) recorded in headless Chromium along the template's camera path, ending on a 3-second end card with the title, the short template URL and the remix QR code (design D5).

**Commands (v1):**
- `zullumap render <template>@<version> --data x.geojson --map value=pop_density [--map height=...] --title "..." [--options choices.json] [--basemap file.pmtiles] [--no-recipe] --out ./my-map/` creates the interactive page.
- `zullumap trailer ./my-map/ [--size 1080x1350] --out trailer.mp4` records the fly-through.
- `zullumap remix <map-page-folder | recipe-link | map-page-url> --data mine.geojson --title "..." [--map value=...]` re-renders with new data.
- `zullumap check <template>`: the CI gate (pass conditions below).

**Who decides inside the adaptation rules:** the CLI. For every choice the manifest allows (class method, class count, height scale, zoom, pitch, label density), the CLI computes a deterministic default from the data, so the same data + template + options + zullumap version give the same map. An agent or person may override any choice through flags or an `--options` JSON file. The CLI validates every override against the adaptation rules and rejects values outside them with an error naming the rule. The agent never edits `deck.json` directly; the SKILL.md teaches agents to pass choices only through `--options`.

**What the recipe stores, and what remix re-fits:**
- Stored and re-applied exactly: template id + version, the `core` major version that computed it (eng review D13; classification formulas only change in a major release, and remix warns across majors), class method and count, color ramp, height scale, camera preset, label density, any other chosen option.
- Re-fitted on the new data: class break values (stored method and count), map bounds and camera target (within the template's zoom and pitch ranges), label placement.
- Replaced by the remixer: data, slot-to-column mapping and title.

**`recipe.json` and privacy (v1):** lives in the map page folder and contains template id + version, author and license, basemap attribution, the stored choices, the slot-to-column names (e.g. `value → pop_density`) and the title. It never contains file paths or a data hash. The map page itself contains the data, because an interactive map needs it; the user decides where to publish the page. `--no-recipe` leaves out `recipe.json`, the remix button and the QR code.

**The remix link:** `<gallery-host>/t/<template-id>@<version>#r=<choices>` carries only the template id@version and the choices that differ from the template's defaults, as compact base64url, with no title or column names. Target: at most 100 characters, so it fits a QR code of version 6 or lower (41×41 modules) at error-correction level M (eng review D12). The fragment never reaches a server: the template page decodes it in the browser, and `remix` decodes it locally. The QR code appears on the trailer's end card at least 300 px wide on a 1080 px-wide video, and in the interactive page's credits. `render` prints the full link for the post caption. `<gallery-host>` is the project's GitHub Pages site in the 2026 preview; if it moves to a custom domain later, `remix` keeps accepting the old host.

**How `remix` gets the recipe:** a local map page folder (reads `recipe.json`); a recipe link on an accepted gallery host (decoded locally); a published map page URL (fetches `<page>/recipe.json`); anything else stops with "unsupported input: pass a zullumap map page, a recipe link or a map page URL".

**Remix inputs the remixer must give:** `--title` is required (the error shows the original title for reference). Required slots are mapped with `--map`; for remixes from a map page, remix reuses a stored column name when the new data has a column with that exact name (with a note). A recipe link carries no column names, so `--map` is required there. Optional slots (label, height) follow the same exact-name rule, otherwise they're left out.

**Template resolution and versioning:** the registry is the `templates/` folder of the zullumap GitHub repo. Every published version is a git tag (`template/<id>@<version>`) protected by a GitHub tag ruleset so it can't be moved or deleted; a change always means a new version. The gallery build publishes each tagged version as its own static file set at `<gallery-host>/registry/<id>/<version>/` plus a `registry/index.json` of versions and content hashes (eng review D10); `render` and `remix` download only those files, check the content hash, and cache them in `~/.cache/zullumap/templates/`. If a version is missing, remix stops with an error naming the newest version and offering `--template <id>@<version>`. Local templates are used only with an explicit `--template-dir <folder>`; remix never loads a template from a URL inside a recipe. A bare template id (no version) resolves to the newest published version listed in `registry/index.json`.

**Template trust model (amended by eng review D3):** templates are mostly data, with code allowed in one place. `deck.json` and `basemap.json` are declarative JSON; `overlay.html` is HTML/CSS with no scripts. A template may add one optional `effects.js` ES module that implements zullumap's fixed plugin interface (it receives the resolved data, slots and theme, and returns extra deck.gl or three.js layers). Code anywhere else (`<script>` tags, inline event handlers, `javascript:` URLs) is rejected by `check` in CI and by `render`/`remix` every time a template loads (including `--template-dir`). Guardrails for template code: every generated page ships a strict Content-Security-Policy with every directive locked down (`default-src 'none'`; scripts only from the pinned CDN path plus hash-pinned inline scripts; `connect-src`/`img-src` only the basemap host plus `data:`/`blob:`; `worker-src blob:` for MapLibre; fonts only from declared hosts), tested against MapLibre and deck.gl. It blocks background requests to other hosts, but no CSP can stop a script from navigating the page away, so the main defenses against a malicious template are review, the badge, consent and sandboxing on the gallery; registry templates with `effects.js` show a "contains code" badge and get stricter maintainer review; `render`/`remix` ask for `--allow-code` the first time a registry code template is used; `check` runs template code with network blocked. On the gallery, demos of templates with `effects.js` run inside a sandboxed iframe (`sandbox="allow-scripts"` without `allow-same-origin`), so template code can't touch the rest of the gallery site (eng review D11). During `check` and trailer recording, the Playwright context blocks network access except the basemap host, the pinned CDN and the template's declared fonts.

**Basemap (v1):** PMTiles over HTTP range requests from a basemap URL in zullumap's config, defaulting to a Protomaps planet build hosted by the project on static object storage. `--basemap file.pmtiles` uses a local extract. A template may declare `basemap: none`. CI uses a committed low-zoom planet extract (zoom 0-6) so continental and dateline tests have coverage without network. Terrain (DEM) is deferred to the raster milestone.

**Input data (v1):**
- GeoJSON must be WGS84 (EPSG:4326). A `crs` member other than WGS84, or coordinates outside ±180/±90, is rejected with an error asking the user to reproject.
- CSV point data: coordinate columns auto-detected from `lon`/`lng`/`longitude`/`x` and `lat`/`latitude`/`y` (case-insensitive); `--lon`/`--lat` override. No pair found, or projected values, stops with an error naming the detected columns.
- Size: above 20 MB of GeoJSON, `render` warns that the page may load slowly in browsers.

**When the data doesn't fit the template (render and remix):**

| Mismatch | Behavior |
|---|---|
| Wrong geometry type (e.g. points into a polygon template) | Hard error naming the slot and expected type, plus registry templates that accept the data's geometry |
| Mixed geometries in one FeatureCollection | Use matching features; warn with the skipped count. Hard error if none match |
| Missing value or height field | Hard error naming the slot and listing the available columns |
| Non-numeric values in a numeric slot | Numeric strings are coerced; others become "no data" (template's no-data style, zero height) with a warning and count. Hard error only if no numeric values remain |
| Fewer distinct values than classes, or heavy ties | Remove duplicate breaks; the resolved class count becomes the number of unique classes (at least 1). Warn when below the requested count |
| Negative values in a height slot | Hard error unless the template's adaptation rules allow a diverging height scale |
| Title longer than the template's limit | Hard error stating the limit and the length |
| Empty dataset | Hard error |
| Optional slot missing | Render without it, no warning |

**`zullumap check` pass conditions (CI gate):** a pull request is blocked unless all pass:
1. `manifest.json`, `deck.json` and `basemap.json` validate against their schemas; every slot and adaptation rule is well-formed.
2. No JavaScript outside the optional `effects.js` (trust model above); `effects.js` loads, implements the plugin interface, and throwing inside it leaves the base map drawn and fails the check. Inline JSON blocks escape `<` and the overlay renders title and legend values as text only, verified with a fixture whose title and properties contain `</script` (eng review outside voice).
3. Every compatible standard test dataset renders without console errors: points, polygons, lines, skewed values, a single feature, a neighborhood extent, a continental extent, a dateline-crossing extent, and a title at the maximum length.
4. For each render, at each camera preset and at both a 1280 px and a 375 px viewport: title, legend and credits stay inside the viewport and don't overlap (DOM bounding-box check), the data's bounds are in view, and overlay text meets 4.5:1 contrast against its backing (design D10).
5. The legend shows the resolved class count after duplicate breaks are removed (1 for the single-feature dataset).
6. A short smoke trailer (first 1 s of the camera path at 10 fps plus the end card) records without error, and its end-card QR code decodes to the full remix link (at most 100 characters, QR level M) from a frame downscaled to 1080 px wide, both from the clean frame and after re-encoding the smoke trailer at ~2 Mbps H.264 (eng review D12). Full-length trailers are recorded locally on the user's GPU, not in CI (eng review D8).
7. The attribution chip (design D6) is fully visible and unobscured in every render, at 1280 px and 375 px. Viewer-owned controls have fixed slots (MapLibre's required attribution renders inside the credits line; navigation buttons are hidden in favor of gestures and keyboard) and are included in the overlap check.
8. Smoke-trailer frames keep the title below the top 8% and the legend and end-card text above the bottom 15% (design D5 safe zones).

Preview images and the trailer are attached to the pull request for the human review of taste.

**Agent skill:** one SKILL.md that teaches an agent to pick a template, map columns to slots, pass choices only through `--options`, and call `render` then `trailer`. MCP server comes later.

**Gallery:** a static GitHub Pages site. Its build materializes every published template version, so pinned `/t/<id>@<version>` pages and `registry/<id>/<version>/` files exist for all tags (eng review outside voice). Template pages (`/t/<template-id>`, newest version; `/t/<template-id>@<version>`, pinned) show a live interactive demo, the trailer, "what your data needs" (slots), "the agent may adjust" (adaptation rules), the copyable agent prompt and `remix` command, and community maps made with that template; when opened from a recipe link they load the original choices. Map pages are the interactive maps themselves, with a remix panel. Templates and example maps are added by pull request: templates to `templates/<id>/`, example maps to `gallery/maps/<slug>/` (the map page folder made by `render`, including `recipe.json`). Gallery PRs are capped at 10 MB per map page and 8 MB per trailer (checked in CI); trailers and their preview renditions are uploaded as GitHub Release assets of a `gallery-media` release and referenced by URL, so videos never enter git history and Pages only serves pages, posters and the registry (eng re-review D18).

**Three launch templates:**
1. **Extruded choropleth:** polygons extruded by value with a risograph-style palette (the builder's first template).
2. **Night columns:** glowing 3D columns for point data on a dark basemap.
3. **Flow arcs:** 3D arcs between origin-destination points.

Wireframe (2D sketch from before the 3D revision; the map area becomes the interactive 3D canvas): ~/.gstack/projects/jjestrada2-zullumap/juanestrada-main-sketch-20261119-220854.png

**Known implementation risks (for the engineering review):**
- WebGL in headless Chromium for CI and trailers needs software rendering (SwiftShader), which is slow; trailer recording may need a GPU runner later.
- Smooth trailers need frame-by-frame capture (step the camera per frame, screenshot, encode with ffmpeg), not real-time screen recording.
- Dateline-crossing bounds need explicit handling; a naive fit-to-bounds spans the globe.
- Large datasets make the page heavy; binary formats (e.g. FlatGeobuf) may be needed later.
- The viewer runtime is loaded from a pinned CDN version with a Subresource Integrity hash (eng review D6), so old map pages keep their exact engine; pages need internet for the runtime and the default basemap.

## UI design (design review, 2026-11-20)

Decisions from /plan-design-review; each line cites its decision.

- **Template page hierarchy (design D1):** (1) the live 3D map fills the first screen with the template title and one "Remix this style" button; (2) the three remix steps; (3) "what your data needs" (slots) and "the agent may adjust" (rules); (4) community maps made with this template.
- **Map page overlay layout (design D2):** desktop: title top-left, legend bottom-left, the remix button ("Make this map with your data", see approved mockup) bottom-right, credits and QR as one thin line along the bottom. Phones (<600 px): only the title stays on the map; legend, credits and the remix button move into a swipe-up bottom sheet (the button sits full-width under the legend), and the in-page QR is hidden (you can't scan your own screen).
- **Loading and error states (design D3):** every map page shows a still poster image first, with a thin progress bar; the live 3D map fades in over it. The poster is a separate opening-view frame with no overlay saved by `trailer`, inlined as a size-capped `data:` JPEG (≤200 KB) and shown by a small inline bootstrap script that also owns the progress bar and failure messages, so they work even when the CDN runtime can't load (eng re-review), or a screenshot `render` takes only when `--poster` is passed (never based on what is installed, eng re-review D17); without either, the page shows a title card (template background + title + "Loading 3D map…") in its place (eng re-review D16). State table:

  | Feature | Loading | Empty | Error | Success | Partial |
  |---|---|---|---|---|---|
  | Map page | poster + thin progress bar | n/a (render refuses empty data) | no WebGL / context lost: poster stays + "Your device can't show the 3D map — here's a picture of it"; offline or CDN down: poster + "Connect to the internet to explore this map" | live map fades in over the poster | basemap tiles still loading: data layer shows first, basemap fills in |
  | Template page (from `#r=` link) | poster of the template demo + progress bar | n/a | damaged link: "This remix link is damaged — here's the template's default look"; missing version: "This version is gone — showing the newest" | demo with the link's choices | n/a |
  | Code-template demo (sandboxed) | poster + progress bar | n/a | "This template's effects couldn't start" over the poster | live demo | base map drawn, effects failed: same message as a small banner |
  | Community maps list | n/a | "No remixes yet — be the first" + the copyable remix command | n/a (built statically with the gallery) | list of maps | n/a |

- **Phone remix path (design D4):** on phones (<600 px) the template page's remix area reads "Love this look? Make it yours on your laptop" with one button that opens the phone's share sheet (Web Share API; copy-link fallback) carrying the remix link; the `remix` command and agent prompt stay available, collapsed under "Remix now".
- **Journey storyboard:**

  | Step | User does | User feels | Plan specifies? |
  |---|---|---|---|
  | 1 | Sees the trailer autoplay (muted) in the LinkedIn feed | Stops scrolling: "whoa, that's a map?" | trailer first frame + title at second 0 (see D5) |
  | 2 | Taps the caption link or scans the end card QR | Curious, low commitment | end card (D5); short URL |
  | 3 | Lands on the template page on a phone | Sees the same look live, instantly | poster + live map first screen (D1, D3) |
  | 4 | Taps "Make it yours on your laptop" | Saves the intent, no pressure | share sheet (D4) |
  | 5 | Opens the link on a laptop, copies the command or prompt | Confident: one step | remix steps + data needs (D1) |
  | 6 | Runs remix with own data | Delight: their data, that look | remix CLI, clear errors (design doc) |
  | 7 | Posts their own trailer | Pride; the loop restarts | trailer + attribution chip (D6) |

- **Trailer for LinkedIn (design D5):** the map title is visible from frame 0, so the auto-generated thumbnail explains itself; the end card holds 3 s; nothing important sits in the top 8% or bottom 15% of the 1080×1350 frame (LinkedIn's buttons and caption cover those areas); on the end card the short URL is the largest text and the QR (≥300 px) sits beside it.
- **Attribution chip (design D6):** every map page shows a small fixed "made with zullumap · remix" chip in the top-right corner, and the trailer end card shows it below the short URL (outside the safe-zone margins). It looks the same on every template, data-only templates can't hide or restyle it (the viewer draws it outside the template overlay), and `check` fails any template, including code templates with `effects.js`, whose renders don't show the chip fully visible (eng re-review); it links to the template page. With `--no-recipe` the chip reads just "made with zullumap".
- **Gallery and community-map lists (design D7):** an edge-to-edge mosaic of muted, looping trailers with no card borders or shadows; each tile shows its poster image until it scrolls into view, then plays (lazy-play via an IntersectionObserver, at most 3 playing at once, `preload="none"`; the gallery build makes a small preview rendition of each trailer, about 540 px wide at ~1 Mbps, for tiles; eng re-review); one plain text line under each tile (template name · number of community maps merged into the gallery for it). Phones: one full-width tile per row, scrolling like a feed. Template pages use the same tiles for "community maps".
- **zullumap's own visual system (design D8):** run `/design-consultation` before building the viewer chrome and gallery UI, and save the result as `DESIGN.md` (fonts, colors, spacing, motion). Gallery, template pages, remix panel, attribution chip and state messages all follow it; template overlays stay template-styled.
- **Touch and gestures (design D9):** maps embedded in scrolling pages (template page first screen, gallery) ignore swipes until tapped ("Tap to explore" hint; tap outside or scroll to release), so page scrolling never gets trapped; full-page map pages are interactive immediately.
